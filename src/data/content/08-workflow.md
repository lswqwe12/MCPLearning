本章把前面学到的组件与原语串起来，讲解一次完整的 MCP 交互是如何「从用户提问到最终回答」跑通的，以及能力协商如何保证双方协作顺畅。

## 完整工作流程示例

以「Claude Desktop + 文件系统 MCP Server」为例，一次文件相关的问答经历了如下链路：

```text
用户提问 → Claude Desktop (Host) → Claude 模型
    → 需要文件信息 → MCP Client 连接
    → 文件系统 MCP Server → 执行操作
    → 返回结果 → Claude 生成回答 → 显示在 Claude Desktop 上
```

逐步拆解：

1. **用户提问**：用户在 Claude Desktop 输入问题。
2. **模型决策**：Claude 模型判断需要访问文件信息，决定调用文件系统工具/资源。
3. **客户端转发**：MCP Client 把请求转发给文件系统 MCP Server。
4. **服务器执行**：文件系统 Server 执行真实操作（读文件/列目录）。
5. **结果回传**：Server 把结果返回给 Client，再传给模型。
6. **生成回答**：模型基于结果生成最终回答，显示在界面上。

## MCP 工作流架构分层

整个工作流在架构上分为两层：

1. **Host 层**：负责 AI 推理，决定何时调用工具、如何组织上下文。
2. **Protocol 层**：定义通信格式（JSON-RPC）和传输方式（stdio/SSE）。

> 分层意味着：模型「要不要调用工具」是 Host 层的智能决策；「怎么把调用请求发出去、怎么收结果」是 Protocol 层的机械通信。

## 典型交互序列

一次标准的请求-响应交互：

1. 主机发送请求以获取数据或执行工具。
2. 服务器处理请求，访问相关数据源或外部服务。
3. 服务器将结果返回给主机。

## 工具执行流程（序列图）

```text
User ──▶ AI: "Analyze this React project"
AI   ──▶ MCP: Tool call
MCP  ──▶ Tool Server: Execute tool
Tool Server ──▶ MCP: Result
MCP  ──▶ AI: Tool result
AI   ──▶ User: Final response
```

这条序列清晰地展示了「**模型只负责决策，真正的执行在服务器**」的边界。

## 能力协商（Capability Negotiation）

MCP 使用**基于能力的协商系统**：客户端和服务器在**初始化期间**明确声明各自支持的功能。

- **服务器声明能力**：资源订阅、工具支持、提示词模板等。
- **客户端声明能力**：采样支持、通知处理等。
- **双方必须在整个会话期间尊重已声明的能力**：不调用对方未声明支持的能力。
- **额外能力可通过协议扩展协商**：通过扩展机制追加新能力。

能力协商的价值：让双方在**开始协作前**就「对好口供」，避免运行时因能力不匹配而失败。

## 本章小结

- 完整工作流是「模型决策 → 客户端转发 → 服务器执行 → 结果回传」的闭环。
- 架构分为 **Host 层**（智能决策）与 **Protocol 层**（机械通信）。
- 初始化阶段的**能力协商**确保双方协作顺畅。
